# Работа с ветками и pull request

Документ описывает, как вносятся изменения в репозиторий. Он одинаково обязателен для людей
и для ИИ-ассистента (Claude Code), который работает с кодом.

## Ветки

| Ветка     | Назначение                                                       |
| --------- | ---------------------------------------------------------------- |
| `master`  | production. Обновляется только PR из `develop`, вливает владелец |
| `develop` | dev-окружение и база для всей работы                             |
| рабочие   | одна ветка — одна задача, создаётся от свежего `develop`         |

Имя рабочей ветки: `<тип>/<кратко-о-задаче>` латиницей через дефис, например
`feat/mobile-skeleton`, `fix/budget-rounding`, `docs/workflow`.
Типы — те же, что в коммитах (см. ниже).

## Цикл задачи

1. **Ветка.** `git switch develop && git pull --ff-only && git switch -c feat/...`
2. **Работа.** Коммиты небольшие и осмысленные. Перед PR — `pnpm format:check && pnpm check`.
3. **PR в `develop`.** Описание по шаблону (`.github/pull_request_template.md`):
   что сделано, зачем и **как проверить руками**.
4. **Ревью.** Владелец смотрит дифф и проверяет функционально по шагам из описания.
   Замечания исправляются новыми коммитами в ту же ветку (без force-push, чтобы было видно,
   что изменилось после ревью).
5. **Слияние.** Только после явного «ок» от владельца. Ассистент вливает PR сам
   (squash merge), удаляет ветку и обновляет локальный `develop`.
6. **Релиз.** `develop` → `master` — отдельный PR, его создаёт и вливает владелец.

Следующая задача начинается от обновлённого `develop`. Если она зависит от ещё не влитого PR,
ассистент ждёт слияния, а не строит ветку поверх чужой.

## Размер PR

Большой PR трудно проверить. Поэтому задачи **дробятся на самостоятельные части**:

- Каждый PR решает одну задачу и оставляет `develop` рабочим: проект собирается,
  тесты проходят, приложение запускается.
- Каждый PR **проверяется функционально**: в описании есть шаги, которые можно выполнить
  руками, и ожидаемый результат. Если часть пока не видна в интерфейсе (например, правка API),
  шаг проверки — запрос `curl` или тест.
- Ориентир — **до ~400 строк изменений** без учёта lock-файлов, сгенерированного кода
  и перемещённых без изменений файлов. Больше — повод разбить задачу.
- Механические изменения (переименования, перенос файлов, форматирование) идут
  **отдельным PR** без изменения логики.
- Незавершённая функциональность не ломает существующую: новый экран может быть пустым,
  но не должен ломать остальные.

Крупная задача сначала оформляется планом в `docs/` (см. [`docs/mobile-plan.md`](mobile-plan.md)):
список PR с тем, что входит в каждый и как его проверить. План согласуется до начала работы
и обновляется по мере выполнения.

## Коммиты

[Conventional Commits](https://www.conventionalcommits.org/ru/) с описанием на русском:

```
<тип>(<область>): <что сделано>
```

- Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `ci`.
- Области: `api`, `web`, `mobile`, `contracts`, или без области для изменений во всём репозитории.
- Пример: `feat(mobile): нижняя навигация и пустые экраны разделов`.

При squash merge заголовок PR становится заголовком коммита в `develop`,
поэтому заголовок PR пишется в том же формате.

## Перед открытием PR

- [ ] ветка создана от актуального `develop`;
- [ ] `pnpm format:check && pnpm check` проходит локально (то же запускает CI);
- [ ] в описании есть шаги функциональной проверки;
- [ ] документация (README, `docs/`) обновлена, если изменилось поведение или запуск;
- [ ] в диффе нет секретов, `.env` и случайных файлов.
