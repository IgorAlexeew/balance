# План: мобильное приложение (PWA)

Статус: **согласование**. Порядок работы — [`docs/WORKFLOW.md`](WORKFLOW.md): каждый пункт ниже — отдельный PR
в `develop`, который можно проверить и по диффу, и руками.

## Цель

Приложение для телефона, которое устанавливается на домашний экран и открывается во весь экран,
как нативное. Работает с тем же API и теми же данными, что и веб-версия.

## Решения

| Вопрос              | Решение                                                                                               | Почему                                                                                                                                                                               |
| ------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Технология          | **PWA** (Progressive Web App)                                                                         | Самый простой путь: без магазинов приложений, без Mac/Xcode, тот же стек React + Vite. Установка — «Добавить на главный экран»                                                       |
| Где код             | Новый пакет **`apps/mobile`** (`@balance/mobile`)                                                     | Мобильный интерфейс (нижняя навигация, крупные элементы, жесты) заметно отличается от десктопного. Отдельное приложение не усложняет `apps/web` и запускается/тестируется независимо |
| Стек                | React 19 + Vite + React Router + TanStack Query + Tailwind v4 + shadcn/ui, архитектура FSD            | Как в `apps/web`: один набор знаний и инструментов                                                                                                                                   |
| Общий код           | `@balance/contracts` (уже есть) + новый пакет **`packages/api-client`** (http-клиент и хуки запросов) | Запросы к API не дублируются в двух приложениях. UI-компоненты shadcn копируются в `apps/mobile/src/shared/ui` — это штатная модель shadcn                                           |
| Адрес в production  | API отдаёт мобильную сборку по пути **`/m/`** рядом с веб-версией                                     | Один origin → одна cookie сессии, CSRF-проверка не меняется, не нужен отдельный домен                                                                                                |
| Уведомления         | Сначала — существующие уведомления в приложении. Web Push — отдельным этапом после MVP                | Web Push требует VAPID-ключей и доработки планировщика; на iOS работает только для установленного PWA (iOS 16.4+)                                                                    |
| Магазины приложений | Не в этом плане                                                                                       | При необходимости PWA позже оборачивается в Capacitor без переписывания интерфейса                                                                                                   |

## Как запускать и тестировать локально

`pnpm dev` (turbo) запускает все приложения: API на `:3001`, веб на `:5173`, мобильное на `:5174`.
Можно запускать и отдельно: `pnpm --filter @balance/mobile dev`.

Варианты проверки:

1. **На компьютере.** http://localhost:5174/m/ в Chrome с эмуляцией телефона (DevTools → Toggle device toolbar).
   На `localhost` работают service worker и установка PWA — можно проверить почти всё.
2. **На телефоне в той же Wi-Fi сети.** `vite --host` открывает приложение по адресу вида `http://192.168.x.x:5174/m/`.
   Интерфейс работает, но **установить PWA нельзя**: браузеры требуют HTTPS.
3. **На телефоне по HTTPS** — нужно для установки PWA. Поддерживаем два способа, проверяем оба:
   - **Tailscale (основной).** Телефон и компьютер в одной tailnet. `pnpm mobile:tailscale` выполняет
     `tailscale serve` и печатает адрес `https://<компьютер>.<tailnet>.ts.net/m/` с настоящим сертификатом.
     Адрес постоянный, доступен только устройствам вашей tailnet. Нужно один раз: приложение Tailscale
     на телефоне (тот же аккаунт) и в админке tailnet включить **MagicDNS** и **HTTPS Certificates**
     (DNS → HTTPS Certificates).
   - **Cloudflare Quick Tunnel (запасной).** `pnpm mobile:tunnel` запускает `cloudflared` (уже установлен)
     и печатает `https://<случайное-имя>.trycloudflare.com/m/`. Регистрация не нужна, но адрес меняется
     при каждом запуске, адрес публичный, а из России сервис может работать нестабильно.

   Дальше одинаково: открыть адрес на телефоне → демо-вход → «Установить приложение» / «На экран „Домой“».

Вход для тестов — демо-вход (`DEMO_LOGIN=true`, включён в dev).

### Что нужно поменять в API для второго фронтенда

API принимает изменяющие запросы только с `Origin`, равного `APP_URL` (`http://localhost:5173`), —
это защита от CSRF. Запросы со страницы `http://localhost:5174` сейчас будут отклонены (403).
Поэтому первым идёт небольшой PR в API: список дополнительных разрешённых источников `EXTRA_ORIGINS`
(в dev по умолчанию — `http://localhost:5174`). Для Tailscale, туннеля и Wi-Fi dev-прокси мобильного
приложения подставляет `Origin: http://localhost:5174`, так что внешние адреса прописывать в API не нужно.
В production мобильная версия живёт на том же origin (`/m/`), и дополнительные источники не нужны.

## Этапы и PR

Каждый PR оставляет `develop` рабочим. Ориентир по объёму — до ~400 строк без lock-файлов.

### Этап 1. Каркас и проверка на телефоне

**PR 1 — `feat(api)`: дополнительные разрешённые источники `EXTRA_ORIGINS`**

- Конфиг `EXTRA_ORIGINS` (через запятую), `CsrfGuard` проверяет `Origin` по списку, тесты, `.env.example`, README.
- Тесты (API, через HTTP): демо-вход с `Origin` из `EXTRA_ORIGINS` проходит; с чужого `Origin` — 403; с основного `APP_URL` — как раньше; пустой `EXTRA_ORIGINS` не открывает доступ никому лишнему.
- Проверка: `curl -X POST` на `/api/auth/demo` с `Origin: http://localhost:5174` → 200; с `Origin: http://evil.test` → 403.

**PR 2 — `feat(mobile)`: каркас приложения `apps/mobile`**

- Vite + React + Tailwind + React Router, `base: '/m/'`, порт 5174, прокси `/api`, ESLint/steiger/typecheck/test в `pnpm check`.
- Один экран: демо-вход → «Привет, <имя>» → выход. Проверяет всю цепочку: прокси, cookie, CSRF.
- Инфраструктура компонентных тестов: Vitest + Testing Library + MSW. Тесты: неавторизованный пользователь видит экран входа; после «Открыть демо» видит своё имя; после «Выйти» снова экран входа; ошибка API показывается пользователю.
- Проверка: `pnpm dev` → http://localhost:5174/m/ → «Открыть демо» → видно имя пользователя; веб на :5173 работает как раньше.

**PR 3 — `test(mobile)`: e2e-тесты на Playwright**

- Playwright в мобильном профиле (Pixel, iPhone), поднимает API с отдельной тестовой SQLite-базой и мобильное приложение;
  команда `pnpm test:e2e`, запуск в CI.
- Первый сценарий — тот же, что проверяется руками в PR 2: демо-вход → имя на экране → выход.
- Проверка: `pnpm test:e2e` проходит локально и в CI; при сломанном входе (например, остановленном API) тест падает с понятной ошибкой.

**PR 4 — `feat(mobile)`: PWA — манифест, иконки, service worker**

- `vite-plugin-pwa`: манифест (имя, цвета, `display: standalone`, `scope: /m/`), набор иконок, кэш статики. Запросы `/api` не кэшируются.
- Тесты (e2e): манифест отдаётся и содержит имя, иконки и `scope: /m/`; service worker регистрируется; ответы `/api` не берутся из кэша (после выхода данные пользователя не видны).
- Проверка: Chrome на компьютере → значок «Установить» в адресной строке → приложение открывается отдельным окном; DevTools → Application → Manifest без ошибок.

**PR 5 — `chore(mobile)`: проверка на телефоне через Tailscale и Cloudflare**

- Скрипты `pnpm mobile:tailscale` и `pnpm mobile:tunnel`, `server.allowedHosts` для `.ts.net` и `.trycloudflare.com`,
  подстановка `Origin` в dev-прокси, раздел в README с одноразовой настройкой Tailscale.
- Тесты: dev-прокси подменяет `Origin` для запросов с внешнего адреса (запрос с `Host` вида `*.ts.net` проходит CSRF-проверку, запрос напрямую в API с тем же `Origin` — нет). Сами туннели проверяются руками.
- Проверка — для **каждого** способа отдельно: адрес из консоли открывается на телефоне, работает демо-вход,
  приложение устанавливается на домашний экран. Если Cloudflare из России не открывается — фиксируем это в README,
  основной способ остаётся Tailscale.

### Этап 2. Общий код

## Тестирование

Общие правила — в [`docs/WORKFLOW.md`](WORKFLOW.md#тесты): тесты описывают поведение, а не код. Для мобильного приложения:

| Уровень             | Инструмент                                      | Что проверяем                                                                                                                                |
| ------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| API                 | Vitest + supertest (уже есть в `apps/api/test`) | Эндпоинты через HTTP: права доступа, валидация, ответы                                                                                       |
| Логика              | Vitest                                          | Чистые функции: форматирование денег и дат, расчёты                                                                                          |
| Компоненты и экраны | Vitest + Testing Library + MSW                  | Экран глазами пользователя: поиск по ролям и текстам, действия через `user-event`, API подменяется на уровне сети (MSW), а не моками модулей |
| Сквозные сценарии   | Playwright (мобильные профили)                  | Реальные API + приложение + тестовая БД: ключевые сценарии от входа до результата                                                            |

## Риски и открытые вопросы

- **iOS:** установка только из Safari через «Поделиться → На экран „Домой“»; своей кнопки «Установить» там нет — покажем подсказку.
- **Cloudflare из России** может открываться нестабильно — поэтому основной способ проверки на телефоне Tailscale.
  Сам туннель Cloudflare — только для тестов: адрес временный и публичный.
- **Tailscale** требует одноразовой настройки в админке tailnet (MagicDNS, HTTPS Certificates); первый выпуск
  сертификата занимает до минуты.
- **Дублирование UI.** Компоненты shadcn будут в двух приложениях. Если расхождения начнут мешать — отдельной задачей выносим в `packages/ui`.
